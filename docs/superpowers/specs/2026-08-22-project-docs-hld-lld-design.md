# Project docs as Markdown, HLD/LLD Mermaid, and separated spec artifacts

Date: 2026-08-22
Status: approved design, awaiting implementation plan
Branch: feat/electric-design-system (implementation lands on a follow-up branch)

## Problem

Three gaps in the current workspace:

1. `iris/project/{overview,hld,lld,erd,decisions}.html` are managed HTML placeholders
   (`src/commands/lifecycle.ts`, `refreshProjectPlaceholders`). They have no editable
   source, the placeholder tells agents to "write this page with the installed Iris
   skill", but `templates/agents/iris-workspace.md` never mentions them, and the only
   way to fill one is to hand-write HTML that bypasses the safe Markdown/Mermaid
   renderer. In practice the HLD and LLD pages stay empty forever.
2. The Overview's architecture pane says "Automatic HLD projection into this pane
   remains separate work" (`src/templates/pages/overview.ts`).
3. On the Spec page, each OpenSpec change's Proposal, Design, Tasks, Manifest and delta
   specs are stacked into one long detail view (`changeDetailContent` in
   `src/templates/pages/spec-detail.ts`). Feature contracts render only
   problem/goal/tasks and have nowhere to carry a design diagram.

The user wants: each spec change's proposal, design and tasks shown separately, and
HLD/LLD Mermaid diagrams produced when Iris is installed into a repo and when a
feature is built with Iris.

## Decisions already taken

- HLD/LLD content is authored by the agent (Claude Code, Copilot, Codex) into
  Markdown sources that Iris scaffolds and renders. Iris does not derive diagrams
  from OpenSpec `design.md` files; it stays a no-AI CLI.
- Proposal / Design / Tasks / Specs become tabs inside the existing change detail
  view, not separate pages.
- All five project docs move to the Markdown mechanism, not only HLD and LLD.
- Feature contracts gain optional `design.hld` and `design.lld` Markdown sections.
- The Overview architecture pane projects the HLD diagram.

## Non-goals

- No new CLI command. `iris init`, `iris update`, `iris render` and the existing
  content commands cover everything.
- No change to `iris publish` / `iris export` for project docs.
- No automatic code analysis inside Iris. The scaffolds contain placeholder nodes
  such as `Service A`; the agent replaces them.
- No change to the research or contract page pipelines beyond reuse.

## Design

### 1. Project docs as Markdown sources

Source of truth: `iris/project/<name>.md` for `overview`, `hld`, `lld`, `erd`,
`decisions`. These are user-owned, exactly like `iris/research/<id>/index.md`:
`iris init` and `iris update` create them only when missing (`writeIfMissing`) and
never overwrite them.

Output: `iris/project/<name>.html`, CLI-owned, carrying the existing
`data-iris-managed` marker. Regenerated by `iris init`, `iris update`, bare
`iris render` and `iris render --all`. `iris render <id>` continues to reuse the
prior outputs.

Front matter uses the existing research parser (`src/lib/front-matter.ts`):
`title`, `status` (`draft`, `active`, `done`, `archived`), `updated`, `agent`.
Missing values fall back to the first `#` heading (or the doc label), `draft`,
and explicit `not set`. Unknown keys are ignored; malformed lines produce a
path-specific warning rendered on the page and printed to stderr by render.

Loader: new `src/lib/project-docs.ts` modelled on `src/lib/research-workspace.ts`:
reads only the five fixed file names under `iris/project/`, refuses symlinks and
path escapes, caps each file at 256 KB, and returns
`{ items: ProjectDocItem[], warnings: ProjectDocWarning[] }` where
`ProjectDocItem = { name, title, status, agent, updated, body, path, warnings }`.
Reading is sorted by `PROJECT_DOC_NAMES` order.

Renderer: `projectDocHtml(model, item)` in `src/templates/workspace.ts`, reusing
`renderDocument` and `tableOfContents` from `src/templates/pages/research.ts` (or a
shared module extracted from it) and `renderShell` at `depth: 1` with crumbs
`iris / project docs / <Label>`, `mermaid: true`, the `doc-meta` row (status,
agent, updated), any front-matter warnings, the TOC/`doc-single` layout, and the
existing "other project docs" sibling strip. `projectPlaceholderHtml` remains only
for the unmanaged-HTML preservation case described in section 7 and for the
`RETIRED_PROJECT_DOC_NAMES` logic; it is not written when a `.md` source exists.

`WorkspaceModel` gains `projectDocItems: ProjectDocItem[]` and
`projectDocWarnings`. `projectDocs: string[]` (which `.html` files exist) is kept
unchanged so the shell and nav do not change.

### 2. Scaffold content written by `iris init`

Templates live in `src/templates/project-docs.ts` as string constants (one per doc)
so tests can assert on them. Each file has front matter (`title`, `status: draft`),
one sentence of purpose, and headings taken from the current placeholder's "what
belongs here" list. Mermaid skeletons use the same `classDef` block that the agent
skill already documents (focus/svc/db/q/ext/err):

- `hld.md`: `## System map` with a `flowchart LR` of three placeholder nodes
  (`Service A`:svc, `Store`:db, `External`:ext) around a `focus` node named after
  the project directory; `## Boundaries`; `## External dependencies`.
- `lld.md`: `## Key flow` with a `sequenceDiagram` (Caller -> Component -> Store ->
  Component -> Caller); `## Modules`; `## Data shapes`.
- `erd.md`: `## Entities` with an `erDiagram` of two placeholder entities and one
  relation; `## Notes`.
- `overview.md`: `## What this is`; `## How it runs`; `## Where things live`.
- `decisions.md`: `## Decisions` with a four-column table (date, decision, why,
  status) containing one placeholder row.

No repository-specific facts are invented beyond the project directory name, which
the placeholder already uses.

### 3. Spec change detail as tabs

`changeDetailContent(change)` emits, below the existing summary strip and progress
bar, a `[data-tabs="change-<slug>"]` tablist with `role="tablist"` buttons
Proposal, Design, Tasks, Specs, each controlling one `[data-tab-group]` panel with a
matching `data-tab-id`. Proposal is selected by default. Panel contents are the
existing `artifactSection` outputs; Manifest folds into the Specs panel as a
`<details>` above the delta specs. A missing artifact keeps its tab and shows the
existing "This artifact is missing from the change directory" card, so gaps stay
visible. The per-artifact TOC moves inside each panel.

Because change detail HTML is injected from the spec bundle at click time,
`setupTabs()` in `src/templates/script.ts` is refactored into `wireTabs(root)`;
`setupTabs` calls `wireTabs(document)` at load and `showRecord` calls
`wireTabs(slot)` after injection. Activation already dispatches
`iris:visibilitychange`, which triggers Mermaid rendering for figures that just
became visible, so diagrams inside the Design tab render when the tab is opened.
The existing tab keyboard contract (Arrow/Home/End) is unchanged.

### 4. Feature contract `design.hld` / `design.lld`

`schemas/feature.schema.json`: `sections.design` is an optional object with
optional `hld: { md: string }` and `lld: { md: string }` and no other keys.
Existing contracts remain valid.

`iris feature <id>` (`src/commands/draft.ts`) writes
`design: { hld: { md }, lld: { md } }` whose bodies are one-line prompts followed
by the same `flowchart` and `sequenceDiagram` skeletons used for the project docs.

`renderContractPage` `feature` case: when `sections.design` has at least one of
`hld`/`lld`, render a `[data-tabs]` tablist Overview | HLD | LLD | Tasks where
Overview holds Problem and Goal; absent tabs are omitted. When `design` is absent
the current stacked layout is rendered unchanged. The `tasks` meta tile is kept.

### 5. Overview architecture pane

`overview.ts` receives the HLD `ProjectDocItem` (if any). It extracts the first
exact ` ```mermaid ` fence from the body and renders it through the same diagram
host markup the Markdown renderer uses, with the existing "Open HLD" link. If there
is no `hld.md` or it has no Mermaid fence, the empty state is kept and reworded:
"No HLD diagram yet. Edit `iris/project/hld.md` (created by `iris init`), add a
`mermaid` fence, then `iris render --all`." The "separate work" sentence is removed.

### 6. Agent guidance

- `templates/agents/iris-workspace.md`: add two rows to the trigger table
  ("initialized Iris in a repository" -> write `iris/project/hld.md` and `lld.md`
  from the codebase; "built or scoped a feature" -> also fill `design.hld` /
  `design.lld` and refresh the project HLD/LLD when the system shape changed), and
  a "Project docs are Markdown" section listing the five files, the front matter,
  and that the HLD/ERD/LLD skeletons are placeholders to replace with real
  components.
- `templates/agents/iris-commands.md`: extend `feature` with the HLD/LLD steps;
  extend the setup guidance so `/iris:*` surfaces mention the project docs.
- `iris init` final hints: `next: write iris/project/hld.md and lld.md (Mermaid),
  then iris render --all`.
- `docs/cmds.md` (`iris init`, `iris render`, `iris feature`), `README.md` workspace
  table and "Research pages are Markdown" neighbour section, `docs/tech.md`
  ("three editable sources"), `docs/status.md`.

### 7. Preservation and migration

For each name in `PROJECT_DOC_NAMES`, in `refreshProjectPlaceholders`:

| `.md` exists | `.html` state | Action |
| --- | --- | --- |
| yes | any | render `.md` to `.html` (managed) |
| no | missing or managed placeholder | write skeleton `.md`, render |
| no | unmanaged (user-edited) | leave `.html` untouched, do not scaffold, report `preserved user-owned iris/project/<name>.html; move its content to iris/project/<name>.md to let Iris render it` |

The third row reuses the existing `preservedProjectDocs` reporting path.
`RETIRED_PROJECT_DOC_NAMES` handling is unchanged.

### 8. Errors

Unreadable, oversized, symlinked or malformed sources produce a path-specific
warning (on the page, in `iris render` stderr, and in `--json` output) and the
page renders with whatever parsed; a missing source after scaffolding is an
environment error (exit 2) only if the directory cannot be written. Invalid
Mermaid keeps the source-first host per diagram (existing behaviour). Nothing is
invented to fill a gap.

### 9. Testing

New `tests/project-docs.test.ts` (vitest, following `research-pages.test.ts`):

- `iris init` writes five `.md` files, each with front matter; `hld.md`, `lld.md`,
  `erd.md` contain a ` ```mermaid ` fence with the expected diagram type.
- `iris render --all` produces `iris/project/<name>.html` containing the shell,
  `data-iris-managed`, the title, and Mermaid diagram hosts for the three diagram
  docs.
- Editing `hld.md` then running `iris init` again leaves the edit intact and the
  rendered HTML reflects it.
- An unmanaged `iris/project/hld.html` without `hld.md` is preserved, no `hld.md`
  is created, and the preservation message is printed.
- Front-matter warnings surface on the page.
- Overview contains the HLD diagram host when `hld.md` has a fence, and the
  reworded empty state when it does not.

Extended tests: `openspec-browser.test.ts` (four tabs, default selection, missing
artifact visible inside its tab, Manifest inside Specs), `spec-bundle.test.ts`
(bundle HTML contains the tablist), `schema-validation.test.ts` and
`draft-command.test.ts` (`design.hld`/`lld` accepted, skeleton present, unknown
`design` keys rejected), `render-command.test.ts` (feature tabs vs legacy stacked),
`agent-skills.test.ts` (skill text mentions project docs and the HLD/LLD triggers),
`workspace-shell.test.ts` / `html-check` (nav and relative links at depth 1),
`cli-help.test.ts` if help text changes. `pnpm release:check` must pass and the
dogfood workspace under `iris/` is regenerated (`node dist/src/index.js init`
then `render --all`) so `iris/project/*.md` and the updated pages ship with the
change.
