# Vision — Research-Report Design System · "Electric" v2.0

> _Named for the violet android who sees systems with perfect clarity._

> **What this file is:** A self-contained design contract for generating standalone HTML
> **research reports** about codebases: architecture research, code explainers, HLD/LLD docs,
> refactor proposals, and solution designs.
>
> **How to use it:** Hand this entire file to any agent along with a query, e.g.:
> _"Using the attached design system, produce an HTML research report on the retry pipeline
> in packages/queue."_ Every generated page shares identical tokens, class names, libraries,
> and structure — so a future redesign is a token-block swap, not a rewrite.

---

## 1. Non-negotiable rules

1. **Never hardcode colors.** Every color comes from a CSS custom property in §2. No hex/rgb
   anywhere else — inline styles, SVGs, chart configs, and React Flow styles read tokens at
   runtime via `getComputedStyle` (the mermaid `classDef` fallback hexes in §8.2 are the sole
   exception).
2. **Embed §2 tokens + §3 component CSS verbatim** in one
   `<style data-ds="vision-electric" data-ds-version="2">` block. Never edit, reorder, minify,
   or "improve" it. Page-specific CSS goes in a separate `<style data-page>` block and may
   only reference `var(--*)` tokens.
3. **Only the pinned libraries in §7.** No other CDNs, no webfonts, no icon packs besides
   Lucide. Include a library only if the page actually uses it.
4. **Dark mode default**, light via `data-mode="light"` on `<html>`. Every page includes the
   mode toggle; mermaid and charts re-theme on toggle (§8, §10 wiring is mandatory).
5. **Semantic color mapping (§5) is law** across badges, nodes, chart series, and icons —
   cyan is always a service, amber is always a data store, everywhere, in every report.
6. **One report = one HTML file.** Works offline except the pinned CDNs. Responsive to 768px;
   printable (print overrides included in §3).
7. **Every report follows the §6 blueprint.** Readers should be able to navigate any Vision
   report blind because the structure never changes.

## 6. Research report blueprint (fixed section order)

Every report renders these sections in this order; omit a section only if truly empty.
Each is an `h2.section` with an `id`, mirrored in the TOC.

1. **`#tldr` — TL;DR** · `card.hero` · 3–6 bullets: what was found, what to do, risk level.
   Each bullet gets a `.badge` confidence chip: `b-success HIGH` / `b-warning MED` / `b-danger LOW`.
2. **`#question` — Research question & scope** · `c-info` callout with the exact question;
   a "not covered" list to bound scope.
3. **`#map` — System map** · React Flow (§9) for 10+ nodes, else mermaid `flowchart` (§8).
   Colors per §5. One-line caption.
4. **`#territory` — Code territory** · `.filetree` of the relevant subtree; `.hot` marks
   files the report dissects; `.note` annotates each dir's role.
5. **`#findings` — Findings** · The core. Each finding: `h3` + confidence badge → prose →
   `.evidence` block(s) citing `path/file.ts:line` → supporting `pre.code`, tab group
   (§ use `.tabs` for before/after or per-language variants), mermaid `sequenceDiagram`,
   or chart. Deep detail folds into `details.ds`.
6. **`#numbers` — Metrics & measurements** · `grid-4` of `.stat` cards, plus Chart.js (§10)
   for distributions/trends and `.meter` bars for coverage/risk/effort.
7. **`#paths` — Key flows** · `.steps` for the main call path; `.flow` node strips or mermaid
   sequence diagrams per flow; error paths use `.n-danger` / red mermaid class.
8. **`#risks` — Risks & unknowns** · `c-warn` / `c-danger` callouts; each names blast radius
   and a probe to resolve the unknown.
9. **`#proposal` — Proposed direction** · options as a `.tabs` group (one tab per option) with
   a tradeoffs `table.ds`; recommendation as `c-success` callout; migration phases as `.timeline`.
10. **`#appendix` — Appendix & citations** · `details.ds` for raw dumps; `.footnotes` ordered
    list — every `sup.fn` marker in the body resolves here to a `file:line` or commit/PR link.

## 10. Chart.js — fixed theming

One global theme block, then per-chart configs. Series colors strictly follow §5 order.

```html
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.7/dist/chart.umd.js"></script>
<script>
  const css = (v) => getComputedStyle(document.documentElement).getPropertyValue(v).trim();
  const SERIES = () =>
    ['--primary', '--accent-1', '--accent-2', '--accent-3', '--accent-4'].map(css);
  function themeCharts() {
    Chart.defaults.color = css('--muted');
    Chart.defaults.borderColor = css('--border');
    Chart.defaults.font.family = css('--font-sans');
    Chart.defaults.font.size = 12;
    Chart.defaults.plugins.legend.labels.boxWidth = 10;
    Chart.defaults.plugins.legend.labels.usePointStyle = true;
    for (const c of Object.values(Chart.instances)) {
      retint(c);
      c.update();
    }
  }
  function retint(chart) {
    const s = SERIES();
    chart.data.datasets.forEach((d, i) => {
      d.borderColor = s[i % 5];
      d.backgroundColor =
        chart.config.type === 'line'
          ? 'transparent'
          : s[i % 5].replace(')', ' / 0.35)').replace('oklch(', 'oklch(');
      d.pointBackgroundColor = s[i % 5];
    });
  }
  themeCharts();
  document.addEventListener('vision:mode', themeCharts);
  // Every chart: new Chart(ctx, cfg) then retint(chart). Wrap canvas in <div class="diagram"><div class="chart-box">…
</script>
```

Chart-type policy: **bar** = comparisons (latency per endpoint, LOC per module) ·
**line** = trends (error rate, throughput over time) · **doughnut** = composition
(code ownership, dependency share; max 5 slices) · **radar** = multi-axis scoring of
options in §6.9. No pie, no 3D, no gradients.

| ✅ Do                                                      | ❌ Don't                                              |
